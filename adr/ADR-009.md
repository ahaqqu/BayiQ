# ADR-009: Deploy pipeline — sentinel database_id + CI secret injection

**Status:** accepted  
**Date:** 2026-08-13

## Context

`docs/BOOTSTRAP_DEBT.md` tracked the deploy pipeline as a no-op stub. Issue #28 found the pipeline was not merely unactivated — it was broken: workflow D1 names pointed at the upstream template's databases, `wrangler.toml` shipped local-only placeholder `database_id` values, and the deploy scripts echoed stubs.

The `database_id` field in `wrangler.toml` requires a real Cloudflare D1 UUID for remote deploy. We investigated three approaches:

1. **Env var interpolation in `wrangler.toml`** (`database_id = "${D1_DATABASE_ID}"`) — **rejected.** Wrangler does not interpolate environment variables in TOML config (verified against wrangler 4.118.0 source: `parseRawConfigFile` → `parseTOML` reads values literally). The literal string `${D1_DATABASE_ID}` would be sent to the Cloudflare API and rejected.

2. **Commit the real UUID** — **rejected.** The UUID is account-specific; committing it (as the upstream template did) means forks inherit the template owner's database UUID — a security footgun.

3. **Sentinel placeholder + CI secret injection** — **accepted.** A clearly-marked sentinel (`replace-me-with-your-d1-uuid`) is committed. Local dev uses `preview_database_id` (wrangler local mode falls back to `preview_database_id ?? database_id ?? binding`). At deploy time, a CI `sed` step substitutes the sentinel with the real UUID from a GitHub secret before `wrangler deploy`.

## Decision

- `apps/api/wrangler.toml` ships `database_id = "replace-me-with-your-d1-uuid"` (production) and `"replace-me-with-your-d1-uuid-staging"` (staging) — sentinels, not real UUIDs.
- `preview_database_id` is set for both environments so local dev (`--local`) resolves a stable local SQLite database without the real UUID.
- `.github/workflows/deploy.yml` and `staging.yml` inject the real UUID at deploy time: `sed -i "s/replace-me-with-your-d1-uuid/$D1_DATABASE_ID/" apps/api/wrangler.toml` before `bun run deploy`, with the UUID sourced from GitHub secrets (`D1_DATABASE_ID`, `D1_DATABASE_ID_STAGING`).
- Remote D1 migrations use the `DB` **binding** (`wrangler d1 migrations apply DB --remote`), not the database name — the binding is constant across forks and resolved by wrangler from `wrangler.toml`.
- Deploy scripts (`deploy`, `deploy:staging`, `deploy:temp`) run `wrangler deploy` directly — no more echo stubs.

## Rationale

- The sentinel makes the required action obvious: you cannot deploy remotely without replacing it, and the CI step automates that replacement.
- `preview_database_id` decouples local dev from the remote UUID — `bun run db:migrate:local` and `bun run e2e` work without any secrets.
- Using the `DB` binding in workflows (instead of the database name) means the same workflow works for any fork regardless of its `database_name` — the binding is the stable identifier.
- CI secret injection keeps the UUID out of the repo (AGENTS.md: "never commit secrets") while making remote deploy fully automated.

## Consequences

- First remote deploy requires a one-time `wrangler d1 create` provisioning step and setting the GitHub secrets `D1_DATABASE_ID`, `D1_DATABASE_ID_STAGING`, `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`.
- The `sed` substitution mutates the CI working copy only — the committed `wrangler.toml` always has the sentinel.
- The upstream template was fixed in parallel (agentic-project-template PR #53 / issues #50, #51, #52) so future forks inherit the sentinel pattern and the `seed` template-sync command instead of a real UUID.
