# ADR-007: Sync envelope, deletion cascade, and record uniqueness

**Status:** accepted  
**Date:** 2026-08-09

## Context

ADR-003 chose a per-record LWW CRDT synced to D1 but left the payload shape, deletion semantics, and record identity open. The template syncs one flat array of note rows; BayiQ has two entity types (Child, Record) with a parent-child relationship and a cell-keyed record model inherited from the prototype.

## Decision

- The sync envelope carries **two arrays**: `{ schemaVersion, clientVersion, children: ChildRow[], records: RecordRow[] }`. Each array is LWW-merged independently with the same deterministic tie-break rules as the template (`updatedAt`, then payload).
- **Deleting a Child cascades**: the Child row and every Record row of that Child are written as payload-stripped tombstones in the same operation. A resurrected child can never show orphaned records.
- **One Record per (Child, Dose)**: the client store upserts by `(childId, doseId)`. Saving a dose with an existing record edits it; the schedule cell maps 1:1 to a record.

## Rationale

- Two arrays keep the merge function and wire contract simple and type-safe; each entity shape stays homogeneous.
- Cascade tombstones keep client and server state consistent without read-time filtering rules.
- Upsert-by-(childId, doseId) matches the prototype's cell-keyed model and the "cell shows done" UX; `recordId` remains the stable entity id for LWW.

## Consequences

- The server merge runs two independent LWW merges per sync request.
- Deleting a child writes N+1 tombstones; acceptable at this data volume (a few dozen records per child).
- A future "multiple records per dose" feature would require a new ADR and a store migration.
