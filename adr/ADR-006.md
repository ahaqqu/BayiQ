# ADR-006: Anonymous session lifecycle — create-only, 1-year expiry, hashed token

**Status:** accepted  
**Date:** 2026-08-09

## Context

ADR-001 chose anonymous D1 Bearer sessions but left the lifecycle unspecified: how a returning parent "resumes" a session, how long a token stays valid, and how the token is stored server-side. The template stores the raw token in D1 with a 30-day expiry; the spec requires the token be hashed before storage.

## Decision

- `POST /v1/session` is **create-only**: it always mints a new session and returns the Bearer token. The client persists the token in `localStorage` and "resumes" by simply reusing it on every request. There is no resume/validate endpoint.
- Sessions expire after **1 year** (`expiresAt = now + 365 days`). Expired tokens are rejected by the auth guard.
- The token is a random UUID pair; only its **SHA-256 hash** is stored in D1 (`sessions.token_hash`). The raw token is never persisted server-side, so a D1 dump cannot be replayed.

## Rationale

- Create-only keeps the endpoint trivial and matches the template's proven client pattern (store token, reuse).
- 1 year minimizes re-authentication friction for a parent tracking a child over years, while still bounding D1 row growth and leaked-token validity.
- Hashing satisfies the spec's "no custom crypto" constraint — SHA-256 via Web Crypto is platform-provided, not custom.

## Consequences

- A parent who loses their device before real auth lands loses access to the server copy; the local store remains the source of truth until then.
- `sessions` table stores `token_hash` (TEXT, unique) instead of the raw token.
- The client treats a 401 on sync as "session expired" and re-runs the continue flow.
